# Yonder 0.2.0 Release Contract

## 定位

`0.2.0` 是从 `v0.1.1` 生产基线重新构建的首个企业能力版本，不继承已撤回 `0.1.2`、`0.1.3`、`0.1.4` 的实现信誉。它保留远程终端这一唯一核心产品，并增加三项相互配合但职责分离的能力：

1. 企业 relay 在解析目标前验证企业微信或飞书的有效内部成员身份；
2. 活动交互会话原生上传或下载一个普通文件；
3. 企业会话在 Terminal Active 前建立端点到端点的可验证审计。

普通 relay 和普通会话必须继续保持 `v0.1.1` 的使用方式、隐私、性能和 wire 语义。企业能力不改变连接码、OPAQUE、直连优先、relay 回退、PTY/ConPTY 或当前用户权限模型。

## 兼容矩阵

| 场景 | 结果 |
| --- | --- |
| `0.2.0` connect + 普通 relay + `0.1.1` host | 终端可用；文件传输显示不支持；不启用审计 |
| `0.1.1` connect + 普通 relay + `0.2.0` host | 终端行为保持 `0.1.1`；无文件传输；不启用审计 |
| 任一旧 connect + 企业 relay | Enterprise Resolve 不可协商，失败关闭 |
| `0.2.0` connect + 企业 relay + 旧 host | 企业准入可完成，但审计协议不可协商，Terminal Active 前失败 |
| `0.2.0` connect + 企业 relay + `0.2.0` host | 企业准入、强制双端审计、终端和文件传输全部可用 |

新协议固定为：

```text
/yonder/enterprise-resolve/2.0.0
/yonder/file-transfer/2.0.0
/yonder/audit/2.0.0
```

既有 `/yonder/auth/1.0.0`、terminal、registry 和普通 resolve 协议保持不变。不能把拒绝版本的 `1.0.0` 扩展协议当作兼容回退；协商失败必须使用对应的稳定公共错误。

## 责任边界

- `yonder-core`：领域 newtype、状态枚举、固定上限和纯字节 wire/container 编解码；不得依赖网络、文件系统或平台 API。
- `yonder-net`：统一 libp2p transport、唯一连接屏障和应用子流生命周期；不理解 OAuth、文件内容或审计记录。
- `yon-relay`：普通/企业模式选择、企业 OAuth 事务、准入与既有注册/转发；不读取终端、文件和审计内容。
- `yon`：controller/host 终端、文件传输、企业审计记录及离线验证/重放。
- `yonder-config`：分层配置、秘密文件路径和类型安全校验；不持有运行时协议状态。

可替换外部能力使用最小 trait：企业提供商、HTTP 交换、浏览器打开、文件源/接收器、审计身份/账本/时钟。热路径默认静态分发；只有启动时选定的企业提供商集合允许有界动态分发。无替换语义的纯编解码和状态转换不制造形式 trait。

## 并发与资源

网络、企业事务、单个文件传输和单个审计会话分别由单一 owner 持有。跨任务通信只使用有界 channel/oneshot；所有任务都有取消、关闭、背压和故障传播路径。不得为方便引入共享可变全局状态、无界队列或跨任务状态布尔组合。

终端数据保持最高调度优先级。文件每次最多 `64 KiB` 数据块且每会话仅一个活动传输。审计 writer 在 Tokio runtime 外执行有界阻塞 I/O，append-before-effect 操作必须收到写入确认；周期持久化不能把每个键盘块变成一次网络 RTT 或 `fsync`。

## 安全边界

- relay 始终不可信；终端、文件和审计子流复用已认证、加密且唯一的端到端 libp2p 连接。
- 企业认证失败、未知状态、提供商异常、身份状态不明确和审计初始化失败全部失败关闭。
- 普通会话不建立审计身份、不创建审计文件、不产生输入承诺，避免把企业合规策略扩散到个人使用。
- 企业会话不保存原始键盘输入；完整输出属于敏感数据，只保存在各端受保护的本地记录中。
- Windows 审计目录和文件必须复用已验证的安全 ACL 策略；不能创建并复核受保护 DACL 时，企业会话不得进入 Active。

## 交付定义

`0.2.0` 只有在以下证据同时存在时才可发布：

- 普通模式完整回归，三项新能力的单元、集成、属性、故障和端到端测试通过；
- 企业微信和飞书各至少一次真实自建应用认证验收，mock 只能覆盖故障矩阵，不能替代真实 API；
- Windows、Linux、macOS 原生终端、文件和审计行为一致；Linux 实机完成直连/relay、`sch_netem`、断连、资源和 soak 验证；
- 五个可工作的原生 coverage target 独立达门禁，Windows ARM64 按已批准上游例外执行其余门禁；
- 四个 fuzz target 各独立 `30min`，性能、Miri/sanitizer、依赖审计、许可证、静态链接和六 target release 全部通过；
- 每个 target 的 `yon`、`yon-relay` 单文件归档、SBOM、许可证资产、锁文件、SHA-256 与 provenance 完整。

发布后删除 GitHub `v0.1.2`、`v0.1.3` Releases/tags，并以 `--force-with-lease` 把 `main` 整理为 `v0.1.1 -> v0.2.0` 的受控历史；删除相关失败 Actions、临时分支/worktree 和本地悬空对象。外部已下载或缓存的撤回产物无法召回，文档不得作相反承诺。
